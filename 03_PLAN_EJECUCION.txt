======================================================================
0. REGLA PRINCIPAL DEL PLAN
======================================================================

Este documento define CÓMO y EN QUÉ ORDEN se debe construir Naye Fashion Store.

Los documentos que mandan sobre el contenido del proyecto son:

01_REQUERIMIENTOS_COMPLETOS.txt
Define qué debe cumplir el proyecto.

02_BASE_DE_DATOS.txt
Define exactamente cómo debe ser la base de datos.

03_PLAN_EJECUCION.txt
Define el orden de implementación, validación y cierre.

No se debe programar ignorando estos tres archivos.

Regla principal de ejecución:

UNA FASE
->
IMPLEMENTAR
->
EJECUTAR
->
VALIDAR
->
SI FUNCIONA, HACER COMMIT
->
CONTINUAR

Si una fase falla, no se debe avanzar a la siguiente dejando errores
bloqueantes pendientes.

No se debe refactorizar una fase que ya funciona únicamente para hacerla más
elegante.

No se debe cambiar una solución funcional por una alternativa más compleja si
ambas cumplen el mismo requisito.

Prioridad:

1. Funciona.
2. Cumple.
3. Es seguro para el alcance.
4. Es simple.
5. Es reproducible.
6. Es demostrable.
7. Continuar rápidamente.

======================================================================
1. PRINCIPIO DE VELOCIDAD
======================================================================

El desarrollo debe avanzar con el menor número posible de decisiones nuevas.

Ya están definidos:

- proyecto;
- alcance;
- tecnologías;
- modelo de datos;
- ORM;
- framework móvil;
- lenguaje;
- backend;
- base de datos;
- autenticación;
- CRUD principal;
- estrategia de caché;
- estrategia de N+1;
- eager loading;
- procesamiento asíncrono;
- integración Flutter-backend.

No volver a discutir estas decisiones durante la implementación salvo que
exista un bloqueo técnico real.

Regla antiestancamiento:

Si una solución genera complejidad innecesaria y existe otra alternativa
válida que cumple exactamente el mismo requisito, cambiar inmediatamente a la
alternativa más sencilla.

No invertir tiempo en:

- diseños visuales avanzados;
- refactorizaciones preventivas;
- arquitectura empresarial;
- tecnologías adicionales;
- automatizaciones no requeridas;
- pruebas que no aporten a la entrega;
- plataformas que no se utilizarán;
- problemas estéticos mientras exista funcionalidad pendiente.

======================================================================

02_BASE_DE_DATOS.txt
03_PLAN_EJECUCION.txt
.github/copilot-instructions.md

Reglas para cada ejecución del agente:

1. Trabajar únicamente sobre la fase solicitada.

2. No adelantarse a fases posteriores.

3. No modificar 01_REQUERIMIENTOS_COMPLETOS.txt.

4. No modificar 02_BASE_DE_DATOS.txt.

5. No modificar 03_PLAN_EJECUCION.txt salvo instrucción explícita.

7. No agregar tablas.

8. No agregar campos.

9. No agregar tecnologías no solicitadas.

10. No actualizar Flutter.

11. No reemplazar PostgreSQL.

12. No reemplazar Prisma.

13. No instalar Redis ni BullMQ salvo autorización posterior.

14. No agregar Docker salvo que se vuelva estrictamente necesario.

15. No crear una aplicación móvil completa cuando únicamente se necesite

16. Mantener nombres propios del proyecto en español latino.

20. Informar claramente:

    - errores pendientes reales.

======================================================================
6. PROTOCOLO PARA ERRORES
======================================================================

Cuando aparezca un error:

PASO 1
Leer el mensaje exacto.

PASO 2
Identificar el componente que falla.

Ejemplos:

- PostgreSQL;
- Prisma;
- TypeScript;
- Express;
- Flutter;
- Android;
- networking.

PASO 3
Corregir únicamente el problema relacionado.

PASO 4
Ejecutar nuevamente la misma validación.

PASO 5
Si funciona, continuar.

No realizar una reestructuración grande para corregir un error pequeño.

No instalar cinco dependencias para solucionar un problema que puede
resolverse con una configuración sencilla.

Si una alternativa válida y más simple resuelve el requisito, utilizarla.

======================================================================
11. FASE 4 - AUTENTICACIÓN Y CRUD PRINCIPAL
======================================================================

Objetivo:
Implementar primero la funcionalidad académica principal del backend.

Orden obligatorio:

1. autenticación;
2. categorías necesarias;
3. CRUD Producto;
4. paginación;
5. validaciones;
6. errores.

----------------------------------------------------------------------
11.1. Autenticación
----------------------------------------------------------------------

Implementar:

POST /api/autenticacion/iniciar-sesion

Flujo:

1. recibir correo y contraseña;
2. validar formato;
3. consultar Usuario;
4. verificar hash bcrypt;
5. generar JWT;
6. devolver token.

El JWT debe contener:

- id del usuario;
- rol.

No incluir contraseña.

----------------------------------------------------------------------
11.2. Middleware de autenticación
----------------------------------------------------------------------

Crear middleware simple.

Debe:

- leer Authorization;
- validar Bearer token;
- verificar firma;
- verificar expiración;
- recuperar id y rol del token.

No consultar Usuario nuevamente en cada endpoint únicamente para volver a
obtener esos mismos datos.

----------------------------------------------------------------------
11.3. Categorías
----------------------------------------------------------------------

Implementar:

GET /api/categorias

Su objetivo principal es permitir consultar las categorías existentes y
asignarlas a Producto.

Las categorías se cargan inicialmente mediante seed.

No implementar un CRUD completo de Categoria mientras no sea necesario para
cumplir el alcance.

----------------------------------------------------------------------
11.4. CRUD Producto
----------------------------------------------------------------------

Implementar exactamente:

POST /api/productos

GET /api/productos

GET /api/productos/:id

PATCH /api/productos/:id

DELETE /api/productos/:id

No agregar rutas adicionales sin necesidad.

----------------------------------------------------------------------
11.5. Validación Producto
----------------------------------------------------------------------

Zod debe comprobar como mínimo:

- nombre obligatorio;
- talla obligatoria;
- color obligatorio;
- precio > 0;
- stock >= 0;
- idCategoria válido.

La lógica debe comprobar además que la categoría exista.

----------------------------------------------------------------------
11.6. Paginación
----------------------------------------------------------------------

GET /api/productos debe aceptar:

pagina
limite

Valores predeterminados:

pagina = 1
limite = 10

Respuesta:

datos
+
paginacion

No implementar filtros avanzados en esta fase.

----------------------------------------------------------------------
11.7. Eliminación
----------------------------------------------------------------------

DELETE /api/productos/:id debe eliminar físicamente cuando sea válido.

Si el producto ya forma parte de un DetalleVenta, rechazar la eliminación para
conservar integridad histórica.

No agregar eliminación lógica.

----------------------------------------------------------------------
11.8. Respuestas
----------------------------------------------------------------------

Mantener formato:

{
  "exito": true,
  "mensaje": "...",
  "datos": ...
}

Errores:

{
  "exito": false,
  "mensaje": "...",
  "errores": ...
}

No crear varios formatos diferentes.

----------------------------------------------------------------------
11.9. Validación Postman
----------------------------------------------------------------------

Probar mínimo:

LOGIN
- correcto;
- contraseña incorrecta;
- usuario inexistente.

PROTECCIÓN
- endpoint sin token -> 401;
- endpoint con token -> funciona.

PRODUCTO
- crear válido;
- crear precio inválido;
- crear stock inválido;
- categoría inexistente;
- listar;
- paginar;
- consultar existente;
- consultar inexistente;
- actualizar;
- eliminar.

----------------------------------------------------------------------
11.10. Validación técnica
----------------------------------------------------------------------

Ejecutar:

npm run build

No continuar con errores TypeScript.

----------------------------------------------------------------------
11.11. Commit
----------------------------------------------------------------------

Mensaje:

Fase 4 - autenticacion y CRUD de productos

2. validar al menos un detalle;
3. validar cantidad > 0;
4. consultar productos;
5. verificar existencia;
6. verificar stock;
7. calcular subtotales;
8. calcular total;
9. crear Venta;
10. crear DetalleVenta;
11. descontar stock.

Las operaciones de creación y actualización relacionadas deben ejecutarse
mediante una transacción Prisma.

No aceptar el subtotal o total del cliente como valor confiable.

El backend los calcula.

----------------------------------------------------------------------

- no crear Venta;
- no crear DetalleVenta;
- no modificar stock;
- devolver error controlado.
