======================================================================
0. REGLA PRINCIPAL DE ESTE DOCUMENTO
======================================================================

Este archivo define CÓMO se almacenan y relacionan los datos de Naye Fashion
Store.

La base de datos debe mantenerse igual al modelo académico definido
originalmente para el proyecto, aplicando únicamente la corrección autorizada
necesaria para que las relaciones ya planteadas funcionen correctamente.

No se deben inventar nuevas entidades.

No se deben inventar nuevos campos.

No se deben eliminar campos del modelo original.

No se deben cambiar las relaciones planteadas.

No se deben añadir estructuras adicionales por preferencia técnica.

Las únicas correcciones funcionales autorizadas son:

1. Agregar id_categoria en Producto como clave foránea hacia Categoria.

2. Separar correctamente Venta y DetalleVenta, porque en el documento original
   la estructura presentada bajo el nombre Venta contiene realmente los campos
   propios del detalle de venta.

La nueva entidad Venta únicamente contendrá los campos mínimos necesarios para
hacer posibles las relaciones y reglas que ya estaban planteadas:

- id_venta
- id_usuario
- fecha
- total

DetalleVenta conservará los campos que ya estaban definidos originalmente:

- id_detalle
- id_venta
- id_producto
- cantidad
- subtotal

Las demás diferencias que aparezcan entre el documento académico original y
la implementación serán únicamente adaptaciones técnicas necesarias para
PostgreSQL y Prisma, sin cambiar el significado del modelo.

Principio obligatorio:

MISMO MODELO ORIGINAL
+
CORRECCIÓN MÍNIMA AUTORIZADA
+
ADAPTACIÓN TÉCNICA A POSTGRESQL Y PRISMA

MODELO DEFINITIVO

======================================================================
1. FUENTE FUNCIONAL DEL MODELO
======================================================================

El modelo corresponde al proyecto Naye Fashion Store.

El proyecto administra información relacionada con:

- usuarios;
- categorías;
- productos;
- inventario mediante el campo stock de Producto;
- ventas;
- detalle de los productos incluidos en cada venta;
- movimientos financieros.

Las entidades definitivas son exactamente seis:

1. Usuario
2. Categoria
3. Producto
4. Venta
5. DetalleVenta
6. MovimientoFinanciero

No se crearán en esta etapa entidades adicionales como:

- Inventario;
- Stock;
- Rol;
- Permiso;
- Sesion;
- Cliente;
- Proveedor;
- Reporte;
- Carrito;
- Pago;
- Factura;
- Imagen;
- Notificacion.

Si una necesidad puede resolverse mediante las seis entidades ya definidas, se
debe utilizar el modelo existente.

======================================================================
4. ADAPTACIONES TÉCNICAS QUE NO CAMBIAN EL MODELO
======================================================================

4.1. DATETIME

En el documento académico original se utiliza el término DATETIME.

En PostgreSQL se utilizará TIMESTAMP para representar esos valores de fecha y
hora.

Esto no representa un cambio funcional del modelo.

Equivalencia utilizada:

DATETIME del documento
->
TIMESTAMP en PostgreSQL
->
DateTime en Prisma

4.2. DECIMAL

Los campos monetarios definidos como DECIMAL(10,2) se mantendrán con precisión
de 10 dígitos y 2 decimales.

Equivalencia:

DECIMAL(10,2)
->
NUMERIC(10,2) en PostgreSQL
->
Decimal con @db.Decimal(10,2) en Prisma

Los campos monetarios son:

- Producto.precio
- Venta.total
- DetalleVenta.subtotal
- MovimientoFinanciero.monto

No se utilizará FLOAT para estos valores.

4.3. Identificadores con caracteres especiales

Los nombres técnicos utilizados en código y base de datos evitarán tildes y la
letra ñ para simplificar compatibilidad entre PostgreSQL, Prisma, TypeScript,
terminales y archivos.

Ejemplos:

contraseña
->
contrasena

descripción
->
descripcion

Categoría
->
Categoria

Esto no cambia el significado funcional.

4.4. Convención de nombres físicos

Los modelos en Prisma utilizarán PascalCase:

Usuario
Categoria
Producto
Venta
DetalleVenta
MovimientoFinanciero

Los campos utilizarán camelCase dentro de Prisma cuando corresponda.

Los nombres físicos de tablas y columnas en PostgreSQL utilizarán snake_case
en español.

Ejemplo:

DetalleVenta
->
detalle_venta

idUsuario
->
id_usuario

Esta convención es únicamente técnica y no agrega información al modelo.

9. ENTIDAD VENTA
======================================================================

Nombre lógico:
Venta

Nombre físico recomendado:
venta

Propósito:
Representar la cabecera de una venta registrada en el sistema.

Esta entidad forma parte de la corrección autorizada.

El documento original establece:

- Usuario 1:N Venta;
- Venta 1:N DetalleVenta;
- una venta puede contener varios productos;
- una venta debe tener al menos un detalle;
- el total debe ser igual a la suma de los subtotales.

Sin embargo, la tabla presentada originalmente como Venta contiene los campos
que corresponden al detalle.

Por esta razón se separa Venta de DetalleVenta.

No se agregan campos comerciales adicionales.

14. RELACIONES Y CARDINALIDADES
======================================================================

14.1. Categoria -> Producto

Cardinalidad:
1:N

Interpretación:
Una categoría puede contener varios productos.

Cada producto pertenece a una categoría.

Representación:

Categoria 1 -------- N Producto

Clave foránea:
Producto.id_categoria

----------------------------------------------------------------------
14.2. Usuario -> Venta

Cardinalidad:
1:N

Interpretación:
Un usuario puede registrar varias ventas.

Cada venta es registrada por un usuario.

Representación:

Usuario 1 -------- N Venta

Clave foránea:
Venta.id_usuario

----------------------------------------------------------------------
14.3. Venta -> DetalleVenta

Cardinalidad:
1:N

Interpretación:
Una venta puede contener varios detalles.

Cada detalle pertenece a una venta.

Representación:

Venta 1 -------- N DetalleVenta

Clave foránea:
DetalleVenta.id_venta

----------------------------------------------------------------------
14.4. Producto -> DetalleVenta

Cardinalidad:
1:N

Interpretación:
Un producto puede aparecer en múltiples detalles de venta.

Cada detalle referencia un producto.

Representación:

Producto 1 -------- N DetalleVenta

Clave foránea:
DetalleVenta.id_producto

----------------------------------------------------------------------
14.5. Venta <-> Producto

Cardinalidad lógica:
N:M

Interpretación:
Una venta puede contener varios productos.

Un producto puede aparecer en varias ventas.

Esta relación no se implementa como una relación muchos a muchos implícita.

Se resuelve explícitamente mediante:

DetalleVenta

Motivo:
DetalleVenta contiene información propia de la relación:

- cantidad;
- subtotal.

Representación:

Venta 1 ---- N DetalleVenta N ---- 1 Producto

Resultado lógico:

Venta N ------------------------- M Producto

======================================================================
20. INTEGRIDAD DE UNA VENTA
======================================================================

Registrar una venta implica trabajar con:

- Venta;
- DetalleVenta;
- Producto.stock.

El backend deberá procesar la venta de forma consistente.

Flujo lógico mínimo:

1. recibir los productos y cantidades de la venta;
2. consultar los productos necesarios;
3. verificar que cada producto exista;
4. verificar que cada cantidad sea mayor que cero;
5. verificar que exista stock suficiente;
6. calcular cada subtotal;
7. calcular el total;
8. crear Venta;
9. crear los registros DetalleVenta;
10. descontar el stock correspondiente.

La creación de Venta, DetalleVenta y la actualización de stock deben ejecutarse
como una operación transaccional.

Si una parte falla, no debe quedar:

- una Venta sin sus detalles;
- detalles sin una venta válida;
- stock descontado de una venta que no llegó a registrarse;
- una venta confirmada sin actualizar correctamente el stock.

Prisma deberá utilizar una transacción para esta operación.

Esto no agrega una nueva regla del dominio.

Únicamente garantiza técnicamente las reglas de venta ya definidas.

23. NORMALIZACIÓN
======================================================================

El modelo se mantiene relacional y separado por responsabilidades.

----------------------------------------------------------------------
23.1. Primera Forma Normal - 1FN
----------------------------------------------------------------------

Cada atributo almacena un valor individual.

No se guardarán listas dentro de una columna.

Ejemplo incorrecto:

Venta.productos =
"Camisa, Pantalon, Zapatos"

El modelo correcto utiliza:

Venta
+
DetalleVenta

Cada producto vendido se representa mediante un registro independiente en
DetalleVenta.

Por lo tanto, la relación entre una venta y varios productos se mantiene
estructurada.

----------------------------------------------------------------------
23.2. Segunda Forma Normal - 2FN
----------------------------------------------------------------------

Cada entidad posee una clave primaria simple.

Los atributos de cada tabla dependen de su identificador.

Ejemplo:

Producto.id_producto identifica:

- nombre;
- descripcion;
- talla;
- color;
- precio;
- stock;
- categoria asociada.

DetalleVenta.id_detalle identifica:

- venta;
- producto;
- cantidad;
- subtotal.

No se mezclan datos completos de una entidad dentro de otra cuando pueden
obtenerse mediante una relación.

----------------------------------------------------------------------
23.3. Tercera Forma Normal - 3FN
----------------------------------------------------------------------

Las entidades separan información que pertenece a conceptos diferentes.

Producto no guarda:

- nombre completo de la categoría;
- datos completos del usuario;
- datos completos de la venta.

Producto guarda únicamente:

id_categoria

y la información de Categoria se obtiene mediante la relación.

DetalleVenta no duplica los datos completos del producto.

Guarda:

id_producto

La información completa del producto se obtiene mediante la relación.

Venta no guarda los datos completos del usuario.

Guarda:

id_usuario

Esto reduce duplicación y mantiene la información relacionada de manera
estructurada.

El siguiente DDL representa el objetivo estructural de la base de datos.

Prisma será responsable de generar y ejecutar las migraciones del proyecto.

Este bloque sirve para dejar inequívoco el resultado esperado.

CREATE TABLE usuario (
    id_usuario INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    apellido VARCHAR(100) NOT NULL,
    correo VARCHAR(150) NOT NULL UNIQUE,
    contrasena VARCHAR(255) NOT NULL,
    rol VARCHAR(20) NOT NULL,
    fecha_registro TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE categoria (
    id_categoria INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre_categoria VARCHAR(100) NOT NULL UNIQUE,
    descripcion TEXT
);

CREATE TABLE producto (
    id_producto INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_categoria INTEGER NOT NULL,
    nombre VARCHAR(150) NOT NULL,
    descripcion TEXT,
    talla VARCHAR(20) NOT NULL,
    color VARCHAR(50) NOT NULL,
    precio NUMERIC(10,2) NOT NULL CHECK (precio > 0),
    stock INTEGER NOT NULL CHECK (stock >= 0),
    FOREIGN KEY (id_categoria) REFERENCES categoria(id_categoria)
);

CREATE TABLE venta (
    id_venta INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_usuario INTEGER NOT NULL,
    fecha TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    total NUMERIC(10,2) NOT NULL,
    FOREIGN KEY (id_usuario) REFERENCES usuario(id_usuario)
);

CREATE TABLE detalle_venta (
    id_detalle INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_venta INTEGER NOT NULL,
    id_producto INTEGER NOT NULL,
    cantidad INTEGER NOT NULL CHECK (cantidad > 0),
    subtotal NUMERIC(10,2) NOT NULL CHECK (subtotal > 0),
    FOREIGN KEY (id_venta) REFERENCES venta(id_venta),
    FOREIGN KEY (id_producto) REFERENCES producto(id_producto)
);

CREATE TABLE movimiento_financiero (
    id_movimiento INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tipo_movimiento VARCHAR(20) NOT NULL,
    descripcion VARCHAR(200),
    monto NUMERIC(10,2) NOT NULL CHECK (monto > 0),
    fecha TIMESTAMP NOT NULL,
    CHECK (tipo_movimiento IN ('ingreso', 'gasto'))
);

CREATE INDEX idx_producto_id_categoria
ON producto(id_categoria);

CREATE INDEX idx_venta_id_usuario
ON venta(id_usuario);

CREATE INDEX idx_detalle_venta_id_venta
ON detalle_venta(id_venta);

CREATE INDEX idx_detalle_venta_id_producto
ON detalle_venta(id_producto);

25. MODELO PRISMA OBJETIVO
======================================================================

El archivo schema.prisma deberá representar exactamente las seis entidades
definidas.

El siguiente modelo es la estructura objetivo.

generator client {
  provider = "prisma-client"
}

datasource db {
  provider = "postgresql"
}

model Usuario {
  idUsuario     Int      @id @default(autoincrement()) @map("id_usuario")
  nombre        String   @db.VarChar(100)
  apellido      String   @db.VarChar(100)
  correo        String   @unique @db.VarChar(150)
  contrasena    String   @db.VarChar(255)
  rol           String   @db.VarChar(20)
  fechaRegistro DateTime @default(now()) @map("fecha_registro") @db.Timestamp(6)
  ventas        Venta[]

  @@map("usuario")
}

model Categoria {
  idCategoria     Int        @id @default(autoincrement()) @map("id_categoria")
  nombreCategoria String     @unique @map("nombre_categoria") @db.VarChar(100)
  descripcion     String?    @db.Text
  productos       Producto[]

  @@map("categoria")
}

model Producto {
  idProducto  Int            @id @default(autoincrement()) @map("id_producto")
  idCategoria Int            @map("id_categoria")
  nombre      String         @db.VarChar(150)
  descripcion String?        @db.Text
  talla       String         @db.VarChar(20)
  color       String         @db.VarChar(50)
  precio      Decimal        @db.Decimal(10, 2)
  stock       Int
  categoria   Categoria      @relation(fields: [idCategoria], references: [idCategoria])
  detalles    DetalleVenta[]

  @@index([idCategoria])
  @@map("producto")
}

model Venta {
  idVenta   Int            @id @default(autoincrement()) @map("id_venta")
  idUsuario Int            @map("id_usuario")
  fecha     DateTime       @default(now()) @db.Timestamp(6)
  total     Decimal        @db.Decimal(10, 2)
  usuario   Usuario        @relation(fields: [idUsuario], references: [idUsuario])
  detalles  DetalleVenta[]

  @@index([idUsuario])
  @@map("venta")
}

model DetalleVenta {
  idDetalle  Int      @id @default(autoincrement()) @map("id_detalle")
  idVenta    Int      @map("id_venta")
  idProducto Int      @map("id_producto")
  cantidad   Int
  subtotal   Decimal  @db.Decimal(10, 2)
  venta      Venta    @relation(fields: [idVenta], references: [idVenta])
  producto   Producto @relation(fields: [idProducto], references: [idProducto])

  @@index([idVenta])
  @@index([idProducto])
  @@map("detalle_venta")
}

model MovimientoFinanciero {
  idMovimiento   Int      @id @default(autoincrement()) @map("id_movimiento")
  tipoMovimiento String   @map("tipo_movimiento") @db.VarChar(20)
  descripcion    String?  @db.VarChar(200)
  monto          Decimal  @db.Decimal(10, 2)
  fecha          DateTime @db.Timestamp(6)

  @@map("movimiento_financiero")
}
