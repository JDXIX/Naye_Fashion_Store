======================================================================
0. REGLA PRINCIPAL DEL PROYECTO
======================================================================

Este archivo define QUÉ debe cumplir el proyecto Naye Fashion Store.

Todo el desarrollo debe seguir estos requerimientos a rajatabla.

No se deben agregar funcionalidades que no sean necesarias para cumplir lo
solicitado en el proyecto académico.

No se deben eliminar requisitos solicitados en las guías del proyecto.

Cuando existan varias soluciones técnicamente válidas para cumplir un mismo
requisito, se debe elegir la alternativa más simple, rápida de implementar,
fácil de probar, fácil de explicar, segura para el alcance académico y fácil
de reproducir en otro equipo.

Prioridad general del proyecto:

1. Que funcione.
2. Que cumpla los requerimientos.
3. Que sea seguro dentro del alcance del proyecto.
4. Que sea simple de entender.
5. Que sea simple de ejecutar.
6. Que sea simple de demostrar.
7. Que sea reproducible en otro equipo.
8. Evitar sobreingeniería.

No se debe aumentar la complejidad del proyecto sin una necesidad concreta.

No se deben crear capas, patrones, servicios, dependencias, infraestructura o
funcionalidades únicamente por apariencia profesional.

El código debe poder ser comprendido y explicado por un desarrollador junior.

======================================================================
1. IDENTIFICACIÓN DEL PROYECTO
======================================================================

Nombre:
Naye Fashion Store

Tipo de proyecto:
Aplicación móvil multiplataforma con backend propio y base de datos relacional.

Área:
Administración de una tienda de ropa.

Cliente-servidor.

Aplicación móvil desarrollada con Flutter y Dart.

Servidor:

Usuarios principales:
- Propietarios.
- Empleados.

======================================================================
2. PROPÓSITO DEL PROYECTO
======================================================================

Naye Fashion Store tiene como propósito optimizar la administración de una
tienda de ropa mediante el control digital de sus operaciones principales.

El proyecto debe permitir trabajar con la información necesaria para:

- gestionar el inventario de productos;
- consultar existencias;
- registrar ventas;
- actualizar productos;
- controlar ingresos y gastos;
- generar y consultar reportes relacionados con la operación del negocio.

El objetivo es mejorar la organización de la información, reducir errores de
registros manuales y agilizar los procesos administrativos de la tienda.

La aplicación móvil actuará como cliente.

El backend será responsable de:

- recibir solicitudes de la aplicación móvil;
- validar los datos;
- aplicar las reglas de negocio;
- gestionar la autenticación;
- consultar y modificar la base de datos;
- responder mediante una API REST en formato JSON.

La base de datos será responsable de almacenar la información de forma
estructurada y mantener la integridad de los datos.

======================================================================
4. PRINCIPIOS OBLIGATORIOS DE IMPLEMENTACIÓN
======================================================================

4.1. Simplicidad

Se debe utilizar la solución más sencilla que satisfaga completamente el
requisito correspondiente.

Si una funcionalidad puede resolverse correctamente sin agregar una tecnología
adicional, se debe preferir la solución que utilice menos infraestructura.

4.2. Funcionalidad

No se considerará suficiente que el código únicamente exista.

Cada componente necesario debe poder ejecutarse y demostrarse.

4.3. Seguridad

La simplicidad no puede utilizarse como justificación para:

- guardar contraseñas en texto plano;
- exponer secretos;
- aceptar cualquier dato sin validación;
- permitir acceso a endpoints protegidos sin autenticación;
- escribir credenciales directamente en el código;
- exponer información sensible innecesariamente.

4.4. Reproducibilidad

El proyecto debe poder clonarse desde GitHub y configurarse en otro equipo
siguiendo únicamente las instrucciones documentadas en el repositorio.

4.5. Explicabilidad

La solución debe ser suficientemente clara para que durante el video se pueda
explicar:

- qué componente se está mostrando;
- para qué sirve;
- cómo funciona;
- cómo se conecta con los demás componentes.

4.6. No sobreingeniería

No se debe implementar una arquitectura empresarial innecesaria.

No se deben introducir microservicios, contenedores, servicios externos,
colas distribuidas, almacenamiento en la nube u otras herramientas si el mismo
requisito puede demostrarse de forma correcta mediante una solución local y
más sencilla.

en Naye Fashion Store.

resumen relacionado con ventas.

9. ENTIDAD PRINCIPAL PARA CRUD
======================================================================

La entidad principal seleccionada para demostrar el CRUD completo será:

Producto

Motivo funcional:
Producto representa el núcleo del inventario y permite demostrar creación,
consulta, actualización, eliminación, validaciones, relaciones y reglas de
negocio directamente vinculadas con Naye Fashion Store.

Producto debe permitir como mínimo:

- crear;
- listar;
- consultar por identificador;
- actualizar;
- eliminar cuando la integridad de los datos lo permita.

El listado debe soportar paginación.

La consulta individual debe responder correctamente cuando el producto existe
y cuando no existe.

La actualización utilizará PATCH como método principal para mantener una
implementación sencilla de cambios parciales.

No es obligatorio implementar simultáneamente PUT y PATCH.

9.1. Estrategia de eliminación de Producto

Se utilizará eliminación física cuando el producto pueda eliminarse sin romper
la integridad de información histórica.

Si un producto está referenciado por detalles de ventas existentes, no debe
eliminarse físicamente.

En ese caso la API debe rechazar la eliminación con una respuesta de conflicto.

Esta decisión evita agregar un sistema adicional de eliminación lógica si no
es indispensable y preserva los datos históricos de ventas.

======================================================================
10. REGLAS DE NEGOCIO OBLIGATORIAS
======================================================================

Deben mantenerse las reglas planteadas en la definición original del proyecto.

10.1.
No se puede registrar un producto con precio menor o igual a cero.

10.2.
El stock de un producto no puede ser negativo.

10.3.
Cada producto debe pertenecer obligatoriamente a una categoría.

10.4.
No se puede registrar una venta si la cantidad solicitada supera el stock
disponible.

10.5.
El correo electrónico de cada usuario debe ser único dentro del sistema.

10.6.
Toda venta debe tener al menos un detalle de venta asociado.

10.7.
Cada movimiento financiero debe registrarse como ingreso o gasto.

10.8.
El total de una venta debe ser igual a la suma de los subtotales de sus
detalles.

10.9.
La cantidad de cada detalle de venta debe ser mayor que cero.

10.10.
El subtotal de cada detalle debe calcularse a partir de la cantidad y el precio
del producto utilizado en la venta.

10.11.
Al registrar correctamente una venta se debe actualizar el stock de los
productos correspondientes.

La lógica de la venta debe impedir dejar cantidades de stock negativas.

11. AUTENTICACIÓN
======================================================================

El backend debe incluir autenticación funcional.

La autenticación debe permitir que un usuario registrado pueda iniciar sesión
con sus credenciales.

Flujo mínimo:

1. recibir correo y contraseña;
2. buscar el usuario correspondiente;
3. verificar la contraseña contra el hash almacenado;
4. si las credenciales son correctas, generar un JWT;
5. devolver el token;
6. utilizar el token para consumir endpoints protegidos.

El token debe contener únicamente la información mínima necesaria para la
autenticación y autorización del alcance actual.

Información mínima esperada:

- identificador del usuario;
- rol.

No se debe incluir la contraseña dentro del token.

Las contraseñas deben almacenarse utilizando hash bcrypt.

No deben almacenarse contraseñas en texto plano.

11.1. Optimización de autenticación

La validación del token no debe producir consultas redundantes a la base de
datos en cada solicitud cuando la información necesaria ya se encuentra
firmada en el JWT.

El middleware debe validar como mínimo:

- firma del token;
- expiración;
- existencia de la información mínima requerida.

No se agregará una consulta adicional de Usuario en todas las solicitudes si
no existe una regla funcional que la necesite.

Esto debe poder explicarse como parte de la optimización de autenticación.

12. API REST
======================================================================

El backend debe exponer una API REST.

Formato de intercambio:
JSON.

Prefijo recomendado:
/api

Los endpoints deben utilizar métodos HTTP coherentes con la operación.

Métodos requeridos cuando corresponda:

- POST;
- GET;
- PATCH;
- DELETE.

PUT no será obligatorio si PATCH resuelve correctamente la actualización
parcial elegida para el CRUD principal.

12.1. Endpoints mínimos definidos

AUTENTICACIÓN

POST /api/autenticacion/iniciar-sesion
Propósito:
Validar credenciales y devolver un JWT.

PRODUCTOS

POST /api/productos
Propósito:
Crear un producto.

GET /api/productos
Propósito:
Listar productos con paginación.

GET /api/productos/:id
Propósito:
Consultar un producto específico.

PATCH /api/productos/:id
Propósito:
Actualizar parcialmente un producto.

DELETE /api/productos/:id
Propósito:
Eliminar un producto cuando la integridad de los datos lo permita.

CATEGORÍAS

GET /api/categorias
Propósito:
Obtener las categorías necesarias para consultar o asignar la categoría de un
producto.

No se implementará un CRUD adicional de Categoria si no es necesario para
demostrar el alcance solicitado.

Las categorías iniciales pueden cargarse mediante seed.

VENTAS

POST /api/ventas
Propósito:
Registrar una venta con uno o varios detalles.

Debe validar stock y actualizar existencias.

GET /api/ventas
Propósito:
Consultar ventas.

Debe soportar paginación si se devuelve una colección.

GET /api/ventas/:id
Propósito:
Consultar una venta con sus detalles.

MOVIMIENTOS FINANCIEROS

POST /api/movimientos-financieros
Propósito:
Registrar un ingreso o gasto.

GET /api/movimientos-financieros
Propósito:
Consultar los movimientos financieros registrados.

Debe soportar paginación si se devuelve una colección.

REPORTES

GET /api/reportes/resumen
Propósito:
Obtener un resumen sencillo con información ya perteneciente al alcance del
proyecto.

El reporte debe mantenerse simple.

No debe evolucionar a un sistema analítico adicional.

TAREA ASÍNCRONA

POST /api/reportes/generar
Propósito:
Iniciar una tarea de generación o procesamiento de reporte mediante un worker.

El endpoint existe para demostrar el requisito de procesamiento asíncrono
utilizando una funcionalidad que ya pertenece al proyecto.

12.2. Protección de endpoints

El inicio de sesión debe ser público.

Los endpoints que operen información del sistema deben requerir un JWT válido.

No se implementará un sistema complejo de permisos por rol mientras la guía no
lo requiera.

Los roles Propietario y Empleado deben conservarse como parte de Usuario, pero
no se agregarán reglas de autorización no solicitadas.

13. PAGINACIÓN
======================================================================

La operación Read del CRUD principal debe permitir listar registros con
paginación.

Se debe utilizar una solución sencilla.

Parámetros esperados:

pagina
limite

Valores predeterminados sugeridos:

pagina = 1
limite = 10

El backend debe validar que los valores sean positivos y razonables.

Las respuestas paginadas deben indicar como mínimo:

- página actual;
- límite utilizado;
- cantidad total de registros;
- cantidad total de páginas;
- datos de la página solicitada.

La misma estructura puede reutilizarse en otros listados si esto simplifica el
backend.

14. VALIDACIONES
======================================================================

La API debe validar los datos antes de ejecutar operaciones de persistencia.

Deben aplicarse, cuando corresponda:

- obligatoriedad;
- tipo;
- formato;
- longitud;
- rango;
- unicidad.

Ejemplos relacionados directamente con el proyecto:

Usuario:
- correo obligatorio;
- correo con formato válido;
- correo único;
- contraseña obligatoria para autenticación.

Categoria:
- categoría válida cuando se asigne a un producto.

Producto:
- nombre obligatorio;
- talla obligatoria;
- color obligatorio;
- precio numérico mayor que cero;
- stock entero mayor o igual a cero;
- categoría obligatoria.

Venta:
- debe tener al menos un detalle;
- debe existir el producto;
- cantidad entera mayor que cero;
- cantidad no puede superar el stock.

MovimientoFinanciero:
- tipo obligatorio;
- tipo limitado a ingreso o gasto;
- monto mayor que cero;
- fecha válida cuando corresponda.

Identificadores:
- deben tener un formato válido;
- deben corresponder a registros existentes cuando la operación lo requiera.

Las validaciones reutilizables deben centralizarse únicamente cuando esto
reduzca duplicación real.

No se deben crear abstracciones de validación innecesarias.

15. RESPUESTAS JSON ESTANDARIZADAS
======================================================================

El backend debe mantener un formato consistente.

Formato base de éxito:

{
  "exito": true,
  "mensaje": "Descripción breve del resultado",
  "datos": ...
}

Formato base de error:

{
  "exito": false,
  "mensaje": "Descripción breve del error",
  "errores": ...
}

El campo errores debe incluirse únicamente cuando exista información de
validación o detalle que sea útil para el consumidor.

En respuestas paginadas se puede incluir:

{
  "exito": true,
  "mensaje": "Registros obtenidos correctamente",
  "datos": [...],
  "paginacion": {
    "pagina": 1,
    "limite": 10,
    "totalRegistros": 0,
    "totalPaginas": 0
  }
}

No se debe devolver información técnica interna innecesaria al cliente.

======================================================================
16. CÓDIGOS HTTP
======================================================================

La API debe utilizar códigos HTTP apropiados.

Códigos mínimos esperados:

200 OK
Para consultas y operaciones exitosas que devuelvan respuesta.

201 Created
Para registros creados correctamente.

400 Bad Request
Para datos inválidos o solicitudes que no cumplen el formato esperado.

401 Unauthorized
Para ausencia de autenticación o token inválido.

404 Not Found
Para recursos inexistentes.

409 Conflict
Para conflictos como:

- correo duplicado;
- nombre de categoría duplicado si aplica;
- intento de eliminar un producto referenciado por ventas;
- otra condición de integridad equivalente.

500 Internal Server Error
Para errores inesperados del servidor.

No se debe responder siempre con 200 cuando la operación realmente terminó en
error.

21. SEGURIDAD
======================================================================

La guía solicita identificar al menos dos riesgos de seguridad y las medidas
adoptadas.

El proyecto debe cubrir como mínimo los siguientes riesgos.

21.1. Acceso no autorizado

Riesgo:
Una persona podría intentar consumir operaciones protegidas sin autenticarse.

Medida:
JWT y middleware de autenticación.

Los endpoints protegidos deben rechazar solicitudes que no presenten un token
válido.

21.2. Exposición de contraseñas

Riesgo:
Guardar contraseñas en texto plano permitiría comprometer las credenciales si
la base de datos fuera expuesta.

Medida:
Hash bcrypt.

La contraseña original no debe recuperarse ni devolverse en respuestas.

21.3. Datos inválidos enviados a la API

Riesgo:
Una solicitud manipulada puede intentar guardar información inconsistente.

Medida:
Validación mediante Zod y reglas de negocio antes de persistir datos.

Prisma debe utilizarse como vía normal de acceso a PostgreSQL.

21.4. Exposición de secretos

Riesgo:
Subir credenciales o claves al repositorio.

Medida:
Variables de entorno.

El archivo con valores reales debe excluirse de Git.

Debe existir únicamente una plantilla sin secretos reales.

21.5. Tráfico HTTP local durante desarrollo móvil

La actividad permite autorizar de forma acotada el tráfico hacia el backend
local.

La autorización de tráfico sin cifrar debe limitarse al entorno de desarrollo
y al host utilizado.

No debe tratarse como configuración de producción.

La configuración temporal utilizada para desarrollo debe quedar documentada y
debe poder eliminarse antes de cualquier distribución.

23. CACHÉ
======================================================================

Estrategia obligatoria:
cache-aside.

Operación inicial seleccionada:
Listado de productos.

Endpoint relacionado:
GET /api/productos

Implementación:
Caché en memoria.

Funcionamiento esperado:

1. llega una solicitud;
2. el backend busca la clave correspondiente en caché;
3. si existe y no ha expirado, utiliza el valor almacenado;
4. si no existe o expiró, consulta PostgreSQL;
5. guarda el resultado en caché;
6. devuelve la respuesta.

Tiempo de vida inicial definido:
60 segundos.

El TTL podrá modificarse únicamente si durante las pruebas aparece una razón
concreta.

Invalidación explícita:

La caché relacionada con productos debe invalidarse cuando cambien los datos
que afectan al listado.

Como mínimo después de:

- crear un producto;
- actualizar un producto;
- eliminar un producto.

No se debe instalar un servidor de caché externo mientras la caché en memoria
cumpla la demostración académica.

Limitación conocida:
La caché en memoria pertenece a una instancia del backend.

Esta limitación es aceptable para el entorno local académico y debe
mencionarse cuando se expliquen las limitaciones.

======================================================================
24. CONSULTA N+1
======================================================================

La relación seleccionada para analizar el riesgo N+1 será:

Venta -> DetalleVenta -> Producto

Caso de riesgo:
Obtener una lista de ventas y posteriormente ejecutar consultas individuales
adicionales para recuperar los detalles o productos de cada venta.

Debe conservarse evidencia suficiente para explicar el problema antes de la
optimización.

La versión final debe evitar ejecutar una consulta independiente por cada
registro cuando Prisma pueda recuperar la relación de manera más eficiente.

La solución seleccionada será eager loading mediante las capacidades de Prisma
para incluir o seleccionar las relaciones necesarias en una sola operación
lógica.

No se deben cargar campos o relaciones que no sean necesarios para la
respuesta.

======================================================================
25. LAZY LOADING O EAGER LOADING
======================================================================

La guía exige aplicar y justificar una de las dos estrategias.

Estrategia seleccionada:
Eager loading.

Relación:
Venta con DetalleVenta y Producto.

Justificación funcional:
Cuando se consulta una venta para mostrar su contenido, los detalles y los
productos forman parte directa de la información que se necesita presentar.

Cargar esa información junto con la venta evita ejecutar consultas
individuales posteriores por cada detalle.

No se aplicará eager loading indiscriminadamente a todas las relaciones.

Solo debe utilizarse donde la respuesta realmente necesite esos datos.
